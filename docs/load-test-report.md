## 5. 瓶颈分析

### 5.1 QPS 公式验证

```
QPS = 并发连接数 / 平均延迟
3,933 ≈ 200 / 0.051 = 3,921  ✓ 吻合
```

**当前 QPS 瓶颈 = Tomcat 线程数 × (1 / 单请求延迟)**，而非 CPU 或 Redis。

### 5.2 各组件余量

| 组件 | 上限 | 实测使用 | 余量 |
|---|---|---|---|
| Redis | ~13,000 ops/s | ~4,000 ops/s | **3.3x** |
| 服务端 CPU | 多核 | ~2 核 | **充足** |
| 限流器 | 5,000 req/s | 未触及 | - |
| Tomcat 线程 | 500 | ~200 | **2.5x** |
| Lettuce 连接池 | 100 | 充足 | - |

### 5.3 全业务链路耗时拆解

| 阶段 | 操作 | 耗时 |
|---|---|---|
| 布隆过滤器 | 内存位图查询 | <1ms |
| 售罄检查 | `hasKey` (1 Redis RTT) | ~3ms |
| 本地库存获取 | `localStockCache.acquire()` | <1ms |
| Redis Pipeline | SADD+EXPIRE+LPUSH+EXPIRE (1 RTT) | ~3ms |
| JSON 序列化 + 网络 | Spring MVC → HTTP | ~3-5ms |
| **合计** | | **~10-15ms** |

全业务路径比售罄快速通道多 1 次 Redis RTT + Pipeline 操作，延迟翻倍，QPS 减半，与实测一致。

### 5.4 500 连接性能退化

连接数从 200 增至 500 时 QPS 从 3,933 降至 2,964（-25%），原因：
- 本地回环端口争用（ephemeral port 耗尽 + TIME_WAIT）
- 过多连接竞争 Tomcat NIO 线程，上下文切换开销增大
- Lettuce 连接池排队等待

**建议**: 单机压测连接数控制在 200 以内，更高并发需分布式压测。

---

## 6. 结论

| 路径 | 真实 QPS | 瓶颈 |
|---|---|---|
| 售罄快速通道 | **~4,000 req/s** | 200 并发 × 51ms 延迟（单机连接上限） |
| 全业务链路 | **~1,100 req/s** | Redis 双 RTT（hasKey + Pipeline） |
| 库存查询（纯读） | **~2,000 req/s** | Redis 单 RTT |

- 服务端 CPU、Redis、限流器均有余量，QPS 受限于并发连接数与单请求延迟的物理关系
- 突破 4,000 QPS 需要多机分布式压测（增加有效并发连接数）
- 全业务链路优化方向：减少 Redis RTT（如 Lua 脚本合并 hasKey + Pipeline 为一次调用）
